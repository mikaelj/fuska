# Fuska: Let AI Build Your Code — For Real

<center>[Svenska](PITCH-SVENSKA.md)</center>

------

You've probably pasted code and error messages into ChatGPT, got a suggestion, tested it, gone back and asked again. Fuska is something else entirely. It's a system that lets an AI agent plan, build, and review your code — not just suggest it. And unlike a chatbot, Fuska remembers everything between sessions.


## From Chat to Agent

**How you work today:** You copy a function and an error message into ChatGPT. You get a suggestion. You paste it into your editor, run it, get a new error, go back to the chat. The AI has no memory — the next day you start from scratch.

**A code agent is a different beast.** Programs like Claude Code and OpenCode run directly in your project folder. They can *read your files*, *write code*, *run commands*, and *make git commits*. You give an instruction in plain language, the agent does the work. Think of the difference between asking a colleague "how would I solve this?" and giving that same colleague a ticket in Jira and letting them code, test, and commit. Roughly like the difference between googling a recipe and having a chef in the kitchen.

**Why is a code agent worth using?** In short: it sees the full picture. When you paste a function into ChatGPT, the AI only sees what you pasted. A code agent reads your entire codebase — it finds where the function is called, which other modules are affected, which tests exist. It can run your build and see whether the change actually works. The difference is enormous: instead of you being the middleman copying back and forth, the agent does everything in one go. You describe what you want, the agent delivers working code.

But there's a catch. Even code agents suffer from amnesia. Close the terminal or start a new session and everything is gone — the AI has no idea what you did yesterday. It's like getting a new contractor every morning who's never been briefed on the project.

## What Fuska Does

Fuska solves the memory problem with **MegaMemory** — a persistent knowledge graph stored in a local SQLite database that lives in your project. No server, no configuration — just a file in the project directory. Initiatives, phases, plans, decisions, and research findings are stored as interconnected concepts with relationships, searchable via semantic queries. The AI remembers exactly where you are, which decisions have been made, and which requirements apply. But memory is just the foundation. Fuska structures the entire workflow:

- **Initiatives** = what you want to achieve ("Add OAuth login")
- **Milestones** = groupings of phases that make up a release or delivery
- **Phases** = bounded chunks of work with clear goals and requirements
- **Plans** = task lists with dependencies, generated by the AI
- **Tasks** = concrete steps with acceptance criteria that the agent implements

Each phase follows a simple lifecycle: **design → plan → build → review**. You can run the steps manually one at a time, or let Fuska run the entire chain automatically with a single command — either as `/fuska-do` inside the code agent or as `fuska do` directly in the terminal.

And here's the crucial difference: before a single line of code is written, the plan is reviewed by a **dynamic expert panel** — three specialised AI reviewers assembled based on your specific plan. A base reviewer always watches over code quality and testability. A contextual reviewer is chosen based on project type — for instance, a security reviewer for web projects or a resource reviewer for embedded systems. The third is a domain expert chosen dynamically based on the plan's content: if it involves OAuth you get a security veteran, if it involves databases you get a data architect, if it involves payments you get a Stripe expert.

If two reviewers independently flag the same issue, the severity is automatically escalated. All of this happens before the build even starts.

Then a builder agent implements the code. But the work isn't done yet — a **code reviewer agent** examines the actual diff, checking for bugs, security issues, and deviations from the plan. If it finds problems, the builder fixes them automatically — up to three review-fix iterations before you're asked to intervene. Only after the code passes review does it reach commit stage.

And you're not locked into the formal workflow to benefit from plan checking. If Fuska is initialized, you can ask the AI at any time to run a plan through the checker — just describe your approach in the conversation. The same expert panel reviews it on the spot. Think of it as having your architecture review panel on speed dial.

Git commits don't happen automatically after each step — you choose the strategy yourself: one commit per task, per plan, or per phase. You can also approve each commit manually. Clean history, but on your terms.

## A Concrete Example

You type: `/fuska-do verified implement OAuth login with Google and GitHub`

1. A **research agent** investigates OAuth2 flows, analyses your existing login patterns, and identifies security concerns.
2. A **planner agent** creates a task list with dependencies and security checks.
3. Three **reviewer agents** validate the plan — code quality, security, and OAuth expertise.
4. A **builder agent** implements each task with atomic commits.
5. A **code reviewer agent** examines the diff for bugs, security holes, and plan deviations — if it finds issues, the builder fixes them automatically (up to 3 iterations).
6. A **verification agent** checks that the result actually delivers what the plan promised.

You approve, and it's done. Six agents have worked in sequence, each with their own speciality. You never had to leave the editor. The same thing works with `fuska do verified` directly in the terminal. And if you want more control, you can run each step separately — `/fuska-design`, `/fuska-plan`, `/fuska-build`, `/fuska-review` — exactly as you like.

## See It Happen

That was a hypothetical example. Here's what an actual `/fuska-do checked` session looks like — a real task, real agents, real bug caught.

**The task:** `fuska config` showed misleading percentages for workflow modes. The user ran `/fuska-do checked` to fix it.

**What happened:** The planner proposed a focused 1-file, 5-location edit. The plan-checker validated scope and completeness. The builder implemented all changes. Then the code reviewer found a blocker:

> `this.config.workflow.workflow.mode` — a double property access that would silently return `undefined` and break the display in one of four locations.

The orchestrator didn't blindly trust the review. It read the actual file, ran `git diff`, and verified the code on disk was correct — the bug existed only in the diff context passed to the reviewer. It re-ran the review with the verified diff, which passed clean.

## Why It Matters

**Persistent memory.** Friday at four o'clock you close the editor in the middle of chapter 2. Monday morning you run `/fuska` — it shows exactly which chapter, which task, and what comes next. No manual saving, no resume command. Your position is always current.

**Quality assurance before coding.** Plans are validated *before* a single line of code is written. It's like having an architecture review before breaking ground, instead of trying to fix load-bearing walls after the fact.

**Intelligent git messages.** Each task produces a commit, but the message isn't written based on the diff alone. A dedicated agent reads the actual code, the plan behind it, and the existing commit history, then crafts a message that describes *why* the change was made — not just *what* changed. The history looks as though a meticulous senior developer wrote every message by hand.

**Automatic mapping.** Fuska maps your codebase — architecture, domains, dependencies — so the AI understands the context. It knows that `PaymentService` belongs to the payments domain, not because you told it, but because it analysed the imports.

## The Quality Ladder: Why Process Beats Improvisation

You can already use Claude Code or OpenCode to build code today. But *how* you use the agent determines the quality of the result. Think of it as four levels:

**Level 1: "Just build."** You type "implement OAuth login" and let the agent run. It works — sometimes. The problem is that the agent makes hundreds of microscopic decisions without you knowing. Which OAuth variant? Where are tokens stored? How are expired sessions handled? The agent guesses, and guesses stack on top of each other. The result may look right but have hidden problems that surface weeks later. It's like asking a carpenter to build a room with no blueprint — it might look fine, but it might not be structurally sound.

**Level 2: "Plan, then build."** You ask the agent to make a plan first, read through it, and then say "go". Quality already improves noticeably at this level. Why? Planning forces the AI to break the problem into parts, think through dependencies, and articulate what needs doing and in what order — *before* it writes a single line of code. You also get a chance to catch incorrect assumptions early, when they're still cheap to fix. Same principle as sketching the architecture before you start coding — you don't just write `main()` and hope for the best.

**Level 3: "Plan, validate, then build."** Now you ask the agent not only to plan but also to review its own plan. That adds another layer — but with a limitation: it's still the *same* AI reviewing its own work. Rather like proofreading your own writing — you'll catch typos but rarely spot structural problems. On top of that, you're doing all of this manually: you write the prompt for the plan, then a new prompt for the validation, then a third for the build. It works, but it requires *you* to know which questions to ask.

**Level 4: Fuska.** Here, three things happen that the manual levels cannot provide:

*Separate agents with distinct roles.* The planner agent and the reviewer agents are *different* AI sessions with different system instructions. The reviewers don't know what the planner was "thinking" — they only see the plan and attack it as outsiders. This eliminates the self-confirming bias. It's the difference between having a colleague review your code and reviewing it yourself.

*Dynamic expertise.* The reviewers are chosen based on what the plan is about. A generic AI prompt asks generic questions. A security veteran knows that OAuth tokens shouldn't be stored in `localStorage`, that the PKCE flow is needed for public clients, that refresh tokens require rotation. That knowledge is baked into the reviewer's system instruction — you don't need to come up with the questions yourself.

*Cross-validation.* When two independent reviewers flag the same issue without having seen each other's responses, the system knows it's a real risk, not a false positive. Severity is escalated automatically. That's a signal that never arises when a single agent reviews itself.

The result: each step up the ladder reduces the risk of problems reaching production code. Just building is like driving without sat nav. Planning first is like checking the map before you drive. Validating the plan is like having a passenger double-check the map. Fuska is like having three navigators, each a specialist in different types of road — who raise the alarm if they independently spot the same hazard ahead.

## Fuska versus GSD — An Honest Comparison

Fuska builds on **GSD** (Get Shit Done) — an earlier system with the same core idea: structured AI-driven development with phases and plans. The choice between them isn't obvious. They solve the same problem but make different trade-offs.

### Where GSD Is Better

**Readability.** GSD saves everything in markdown files in a `.planning/` directory. You can open any file in any editor and read requirements, plans, and decisions directly. `git diff .planning/` shows exactly what changed, line by line. `git blame` works on requirement files. Fuska's MegaMemory is a binary SQLite file — you can't diff it in git, and to view a concept you need to either run a command or use a SQLite client. That's a genuine drawback for anyone who wants full visibility without tooling.

**Simplicity for quick tasks.** GSD's `/gsd-quick` requires no choices — you run it and things happen. Fuska's `/fuska-do` requires you to choose between four work modes. For a simple bug fix or a typo, that's unnecessary friction. Fuska does offer the `planned` mode which skips review, but you still have to *know* that's what you want.

**Simpler mental model.** GSD has 14 agents with a fixed flow — you don't need to think about which ones run. Fuska has 20 agents and four work modes. On the other hand: if you choose the `planned` mode in Fuska, you run *fewer* steps than GSD's standard flow, and MegaMemory requires significantly fewer tool calls to load context compared to GSD's file-based reading. In practice, Fuska can be faster — but you need to understand the mode selection.

**Fewer dependencies.** GSD only needs OpenCode and git. Fuska additionally requires Node.js, npm, and MegaMemory as an installed package. More dependencies means more things that can break during upgrades. On the other hand, Fuska's CLI tools give a lot back — see below.

**No startup cost.** GSD maps the codebase on demand. Fuska runs automatic mapping at `init` which takes 30–60 seconds and costs tokens — even if you just want to try the tool on a small project.

### Where Fuska Is Better

**Session memory that actually works.** Close the editor whenever you want — next time you run `/fuska`, it knows exactly which chapter, which task, and what comes next. No pause command, no resume command, no manual saving. GSD requires you to run `/gsd-pause-work` before stopping and `/gsd-resume` to get back — skip either step and context is lost.

**Dynamic expert panel.** Three specialised reviewers assembled based on the project and the plan, compared to GSD's single generic reviewer. Cross-validation — when two independent reviewers flag the same issue — automatically escalates the severity. This catches categories of bugs that a lone reviewer misses.

**Simpler lifecycle.** GSD's phase model is called discuss → plan → execute → verify — four steps that are always run manually, one command at a time. Fuska's equivalent is called design → plan → build → review, with clearer naming and the option to run the entire chain automatically via `/fuska-do` or `fuska do` in the terminal. If you want manual control, you can still run each step separately, just as in GSD — but you don't have to if you'd rather not.

**Flexible work modes.** `/fuska-do` with four modes gives you control over how much review a task deserves. GSD's `/gsd-quick` always runs without review — you can't choose to validate a quick task even if it turns out to be more sensitive than you thought.

**Better git messages.** A dedicated commit agent reads the plan, the actual code, and the existing history to craft messages that explain the intent. GSD's commit messages are generated as a side job by the execution agent.

**Domain mapping and code queries.** Fuska can map business domains separately from technical architecture — it knows that `PaymentService` belongs to the payments domain. GSD lacks this entirely. You can also query the mapping directly: "where is authentication handled?", "which files import OrderService?", "is there any unused exported code?". This works both as `/fuska-ask` inside the code agent and as `fuska ask` in the terminal — the latter without LLM cost. You get answers based on the indexed import graph instead of the agent trawling through the file tree every time.

**Model selection.** Fuska supports any model via configurable profiles — you can use an expensive model for planning and a cheaper one for building. GSD is more locked to specific models.

**CLI without LLM cost.** Fuska has its own command-line tool that lets you do a lot without starting an AI agent: view project status, switch initiatives, configure profiles, export the knowledge graph to markdown, manage git worktrees, and more. GSD has no CLI at all — all interaction goes through the code agent, which means every status check costs tokens. With Fuska's CLI you can orient yourself and administer the project without paying for an LLM session.

**Scale.** MegaMemory is 700 times faster for compound queries in projects with hundreds of concepts. For a small project with ten phases there's no noticeable difference — but for a project that lives for six months with multiple initiatives, it matters.

### Summary

GSD is a better fit if you want a simple, transparent system with no extra dependencies — particularly for shorter projects and quick jobs where you want to read all project data directly in the editor. Fuska pays off when the project lives long enough for session memory, domain mapping, and systematic plan review to repay their startup cost. The choice isn't about which is "better" — it's about how large and long-lived your project is.

## Getting Started

Fuska is, in short, a project management system for AI-driven development. Instead of chatting your way to code line by line, you get an entire chain of specialised agents that research, plan, review, build, and verify. And they remember everything for next time.

```
npm install -g fuska-magistern && fuska init
```

Works with OpenCode and Claude Code. All you need is Node.js and a terminal.
